# 安全部署AI代理

> 本指南介绍如何通过隔离、凭证管理和网络控制来安全部署Claude Code和Agent SDK

Claude Code和Agent SDK是强大的工具，能够代表您执行代码、访问文件以及与外部服务交互。与任何具有这些能力的工具一样，经过深思熟虑的部署能确保您在获得收益的同时保持适当的控制。

与遵循预定义代码路径的传统软件不同，这些工具会根据上下文和目标动态生成其操作。这种灵活性是其有用之处，但也意味着其行为可能受到它们所处理的内容的影响：文件、网页或用户输入。这有时被称为提示注入。例如，如果某个仓库的README包含非常规指令，Claude Code可能会以操作员未预料到的方式将这些指令纳入其操作中。本指南涵盖了降低此风险的实用方法。

好消息是，安全部署代理并不需要特殊的基础设施。运行任何半受信代码所遵循的相同原则在这里同样适用：隔离、最小权限和纵深防御。Claude Code包含多项安全功能以应对常见关切，本指南将详细介绍这些功能，并为有需要者提供额外的加固选项。

并非所有部署都需要最高级别的安全。在笔记本电脑上运行Claude Code的开发者与在多租户环境中处理客户数据的公司有不同的需求。本指南呈现的选项范围从Claude Code的内置安全功能到加固的生产架构，以便您选择最适合自身情况的方案。

## 威胁模型

代理可能因提示注入（嵌入在它们所处理的内容中的指令）或模型错误而采取非预期操作。Claude模型设计具有抵抗性；评估详情请参见[模型概述](https://platform.claude.com/docs/en/about-claude/models/overview)和您所部署模型的系统卡。

然而，纵深防御仍是良好的实践。例如，如果代理处理一个恶意文件，该文件指示它将客户数据发送到外部服务器，网络控制可以完全阻止该请求。

## 内置安全功能

Claude Code包含多项安全功能以解决常见关切。完整详情请参见[安全文档](/zh/security)。

* **权限系统**：每个工具和bash命令都可配置为允许、阻止或提示用户批准。使用glob模式创建规则，如“允许所有npm命令”或“阻止任何包含sudo的命令”。组织可以设置适用于所有用户的策略。参见[权限](/zh/permissions)。
* **用于权限的命令解析**：在执行bash命令前，Claude Code将其解析为抽象语法树并将结果与您的权限规则匹配。无法清晰解析或不符合允许规则的命令需要明确批准。一小部分结构，如`eval`，无论允许规则如何，始终需要批准。这是一个权限门控，而非沙箱；它不会根据命令的目标路径或效果推断其是否危险。
* **网页搜索摘要**：搜索结果被摘要处理，而不是将原始内容直接传递到上下文中，从而降低了来自恶意网页内容的提示注入风险。
* **沙箱模式**：bash命令可以在限制文件系统和网络访问的沙箱化环境中运行。详情请参见[沙箱文档](/zh/sandboxing)。

## 安全原则

对于需要在Claude Code默认设置之上进行额外加固的部署，以下原则指导着可用的选项。

### 安全边界

安全边界将不同信任级别的组件隔离开来。对于高安全性的部署，您可以将敏感资源（如凭证）置于包含代理的边界之外。如果代理环境内发生问题，边界之外的资源仍然受到保护。

例如，您可以不在代理环境中直接暴露API密钥，而是运行一个代理环境外部的代理，将密钥注入请求中。代理可以进行API调用，但它永远不会看到凭证本身。这种模式适用于多租户部署或处理不受信任内容时。

### 最小权限

必要时，您可以将代理限制为其特定任务仅需的能力：

| 资源                | 限制选项                                  |
| ------------------- | ----------------------------------------- |
| 文件系统            | 仅挂载所需目录，优先使用只读              |
| 网络                | 通过代理限制为特定端点                    |
| 凭证                | 通过代理注入，而非直接暴露                |
| 系统能力            | 在容器中放弃Linux能力                     |

### 纵深防御

对于高安全环境，叠加多种控制措施可以提供额外保护。选项包括：

* 容器隔离
* 网络限制
* 文件系统控制
* 在代理层进行请求验证

正确的组合取决于您的威胁模型和操作要求。

## 隔离技术

不同的隔离技术在安全性强度、性能和操作复杂性之间提供了不同的权衡。

  在所有这些配置中，Claude Code（或你的 Agent SDK 应用程序）都运行在隔离边界（沙箱、容器或虚拟机）内部。以下描述的安全控制措施限制了代理在该边界内可访问的范围。

| 技术                | 隔离强度                     | 性能开销       | 复杂性        |
| ------------------- | ---------------------------- | -------------- | ------------- |
| 沙箱运行时          | 良好（安全默认设置）         | 非常低         | 低            |
| 容器 (Docker)       | 依赖配置                     | 低             | 中等          |
| gVisor              | 优秀（需正确配置）           | 中/高          | 中等          |
| 虚拟机 (Firecracker, QEMU) | 优秀（需正确配置）     | 高             | 中/高         |

### 沙箱运行时

对于无需容器的轻量级隔离，[sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime) 在操作系统层面强制执行文件系统和网络限制。

其主要优势在于简洁性：无需 Docker 配置、容器镜像或网络设置。代理和文件系统限制是内置的。您只需提供一个指定允许的域和路径的设置文件。

**工作原理：**

*   **文件系统**：使用操作系统原语（Linux 上为 `bubblewrap`，macOS 上为 `sandbox-exec`）来限制对配置路径的读写访问。
*   **网络**：移除网络命名空间（Linux）或使用 Seatbelt 配置文件（macOS），将网络流量通过内置代理进行路由。
*   **配置**：基于 JSON 的域和文件系统路径白名单。

**配置：**
```bash
npm install @anthropic-ai/sandbox-runtime
```
然后创建一个配置文件，指定允许的路径和域名。

**安全注意事项：**

1. **同主机内核**：与虚拟机不同，沙箱进程共享主机内核。内核漏洞理论上可能导致逃逸。对于某些威胁模型而言这是可接受的，但如果您需要内核级隔离，请使用 gVisor 或单独的虚拟机。

2. **无 TLS 检查**：代理根据客户端提供的主机名对域名进行白名单放行，并不终止或检查加密流量。沙箱内运行的代码可能使用[域名前置](https://en.wikipedia.org/wiki/Domain_fronting)或类似技术来访问白名单之外的主机。如果您的威胁模型需要更强的保障，请配置一个[TLS 终止代理](#流量转发)。有关更多详情，请参阅[沙箱安全限制](/zh/sandboxing#security-limitations)。另外，如果代理对某个允许的域名拥有宽松的凭据，请确保它无法利用该域名触发其他网络请求或泄露数据。

对于许多单开发者和 CI/CD 用例，sandbox-runtime 只需最少的设置即可显著提高安全门槛。以下各节将介绍在需要更强隔离性的部署中使用的容器和虚拟机。

### 容器

容器通过 Linux 命名空间提供隔离。每个容器都有自己的文件系统、进程树和网络栈视图，同时共享主机内核。

一个经过安全加固的容器配置可能如下所示：
```bash
docker run \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  --security-opt seccomp=/path/to/seccomp-profile.json \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=100m \
  --tmpfs /home/agent:rw,noexec,nosuid,size=500m \
  --network none \
  --memory 2g \
  --cpus 2 \
  --pids-limit 100 \
  --user 1000:1000 \
  -v /path/to/code:/workspace:ro \
  -v /var/run/proxy.sock:/var/run/proxy.sock:ro \
  agent-image
```
以下是每个选项的功能说明：

| 选项                               | 用途                                                                                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `--cap-drop ALL`                   | 移除可能用于权限提升的 Linux 功能，如 `NET_ADMIN` 和 `SYS_ADMIN`                                                                                       |
| `--security-opt no-new-privileges` | 防止进程通过 setuid 二进制文件获取权限                                                                                                                 |
| `--security-opt seccomp=...`       | 限制可用的系统调用；Docker 默认阻止约 44 种，自定义配置文件可阻止更多                                                                                  |
| `--read-only`                      | 使容器的根文件系统不可变，防止代理持久化更改                                                                                                           |
| `--tmpfs /tmp:...`                 | 提供一个可写的临时目录，在容器停止时清除                                                                                                               |
| `--network none`                   | 移除所有网络接口；代理通过下面挂载的 Unix socket 进行通信                                                                                             |
| `--memory 2g`                      | 限制内存使用以防止资源耗尽                                                                                                                             |
| `--pids-limit 100`                 | 限制进程数量以防止 fork 炸弹                                                                                                                           |
| `--user 1000:1000`                 | 以非 root 用户身份运行                                                                                                                                 |
| `-v ...:/workspace:ro`             | 以只读方式挂载代码，使代理可以分析但不能修改它。**避免挂载敏感的主机目录，如 `~/.ssh`、`~/.aws` 或 `~/.config`**                                       |
| `-v .../proxy.sock:...`            | 挂载连接到在容器外部运行的代理的 Unix socket（见下文）                                                                                                 |

**Unix socket 架构：**

使用 `--network none` 后，容器将完全没有任何网络接口。代理与外界通信的唯一途径是通过挂载的 Unix socket，该 socket 连接到在主机上运行的代理。此代理可以强制执行域白名单、注入凭据并记录所有流量。

这与 [sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime) 使用的架构相同。即使代理因提示词注入而受到攻击，它也无法将数据泄露到任意服务器。它只能通过代理进行通信，而代理控制着可访问的域。更多详情，请参阅 [Claude Code 沙箱化博文](https://www.anthropic.com/engineering/claude-code-sandboxing)。

**其他加固选项：**

| 选项             | 用途                                                                                                           |
| ---------------- | -------------------------------------------------------------------------------------------------------------- |
| `--userns-remap` | 将容器 root 映射为无权限的主机用户；需要守护进程配置，但可限制容器逃逸造成的损害                                |
| `--ipc private`  | 隔离进程间通信，以防止跨容器攻击                                                                               |

### gVisor

标准容器共享主机内核：当容器内的代码进行系统调用时，它直接到达运行主机的同一内核。这意味着内核漏洞可能导致容器逃逸。gVisor 通过在用户空间拦截系统调用来解决此问题，在它们到达主机内核之前，实现自己的兼容层来处理大多数系统调用，而不涉及真实的内核。

如果代理运行恶意代码（可能是由于提示词注入），该代码在容器中运行并可能尝试利用内核漏洞。使用 gVisor 后，攻击面要小得多：恶意代码需要首先利用 gVisor 的用户空间实现，并且对真实内核的访问权限有限。

要在 Docker 中使用 gVisor，请安装 `runsc` 运行时并配置守护进程：
```json
// /etc/docker/daemon.json
{
  "runtimes": {
    "runsc": {
      "path": "/usr/local/bin/runsc"
    }
  }
}
```
然后使用以下命令运行容器：
```bash
docker run --runtime=runsc agent-image
```
**性能考虑：**

| 工作负载                | 开销                                             |
| ---------------------- | ------------------------------------------------ |
| CPU 密集型计算          | \~0%（无系统调用拦截）                             |
| 简单系统调用             | 慢 \~2 倍                                        |
| 文件 I/O 密集型         | 对于频繁的打开/关闭模式，速度可能慢 10-200 倍            |

对于多租户环境或处理不受信任的内容时，额外的隔离通常是值得付出开销的。

### 虚拟机

虚拟机通过 CPU 虚拟化扩展提供硬件级别的隔离。每个虚拟机运行自己的内核，形成一个强边界。客户端内核中的漏洞不会直接危及主机。然而，虚拟机并不自动比 gVisor 等替代方案“更安全”。虚拟机的安全性在很大程度上取决于管理程序和设备模拟代码。

Firecracker 专为轻量级微虚拟机隔离而设计。它可以在 125 毫秒内启动虚拟机，内存开销不到 5 MiB，通过剥离不必要的设备模拟来减少攻击面。

采用这种方法，代理虚拟机没有外部网络接口。相反，它通过 `vsock`（虚拟套接字）进行通信。所有流量都通过 vsock 路由到主机上的代理，该代理在转发请求前会执行允许列表检查并注入凭证。

### 云部署

对于云部署，您可以将上述任何隔离技术与云原生网络控制相结合：

1.  在没有互联网网关的私有子网中运行代理容器
2.  配置云防火墙规则（AWS 安全组、GCP VPC 防火墙），阻止除指向您的代理之外的所有出站流量
3.  运行一个代理（例如带有 `credential_injector` 过滤器的 [Envoy](https://www.envoyproxy.io/)），它负责验证请求、执行域允许列表、注入凭证并转发至外部 API
4.  为代理的服务账户分配最小化的 IAM 权限，并尽可能通过代理路由敏感访问
5.  在代理处记录所有流量以便审计

## 凭证管理

代理通常需要凭证来调用 API、访问仓库或与云服务交互。挑战在于如何提供此访问权限而不暴露凭证本身。

### 代理模式

推荐的方法是在代理安全边界之外运行一个代理，该代理将凭证注入到出站请求中。代理发送不带凭证的请求，代理添加凭证，然后将请求转发到其目的地。

此模式有几个好处：

1.  代理永远不会看到实际的凭证
2.  代理可以强制执行允许访问的端点列表
3.  代理可以记录所有请求以便审计
4.  凭证存储在一个安全的位置，而不是分发给每个代理

### 配置 Claude Code 使用代理

Claude Code 支持两种方法将采样请求路由通过代理：

**方法一：ANTHROPIC\_BASE\_URL（简单，但仅适用于采样 API 请求）**
```bash
export ANTHROPIC_BASE_URL="http://localhost:8080"
```
这指示 Claude Code 和 Agent SDK 向你的代理发送采样请求，而非直接调用 Claude API。你的代理将接收纯文本 HTTP 请求，可进行检查与修改（包括注入凭证），随后转发至真实 API。

**选项 2：HTTP_PROXY / HTTPS_PROXY（系统级）**
```bash
export HTTP_PROXY="http://localhost:8080"
export HTTPS_PROXY="http://localhost:8080"
```
Claude Code 和 Agent SDK 遵循这些标准环境变量，通过代理路由所有 HTTP 流量。对于 HTTPS，代理会创建一个加密的 CONNECT 隧道：在没有 TLS 拦截的情况下，它无法查看或修改请求内容。

### 实现代理

你可以构建自己的代理或使用现有代理：

* [Envoy Proxy](https://www.envoyproxy.io/)：生产级代理，配备 `credential_injector` 过滤器用于添加认证头
* [mitmproxy](https://mitmproxy.org/)：TLS 终止代理，用于检查和修改 HTTPS 流量
* [Squid](http://www.squid-cache.org/)：缓存代理，具备访问控制列表
* [LiteLLM](https://github.com/BerriAI/litellm)：LLM 网关，支持凭证注入和速率限制

### 其他服务的凭证

除了从 Claude API 进行采样外，代理通常还需要对其他服务（如 git 仓库、数据库和内部 API）进行认证访问。主要有两种方法：

#### 自定义工具

通过 MCP 服务器或自定义工具提供访问，这些工具将请求路由到在代理安全边界之外运行的服务。代理调用该工具，但实际的认证请求发生在外部。该工具调用一个注入凭证的代理。

例如，一个 git MCP 服务器可以接受来自代理的命令，但将它们转发到在主机上运行的 git 代理，该代理在联系远程仓库之前添加认证。代理永远不会看到凭证。

优点：

* **无需 TLS 拦截**：外部服务直接进行认证请求
* **凭证留在外部**：代理只看到工具接口，看不到底层凭证

#### 流量转发

对于 Claude API 调用，`ANTHROPIC_BASE_URL` 允许你将请求路由到可以明文检查和修改它们的代理。但对于其他 HTTPS 服务（GitHub、npm 注册表、内部 API），流量通常是端到端加密的。即使你通过 `HTTP_PROXY` 将其路由到代理，代理也只能看到一个不透明的 TLS 隧道，无法注入凭证。

要修改到任意服务的 HTTPS 流量，而不使用自定义工具，你需要一个 TLS 终止代理，它解密流量、检查或修改它，然后在转发前重新加密。这需要：

1. 在代理的容器外部运行代理
2. 将代理的 CA 证书安装到代理的信任存储中（以便代理信任代理的证书）
3. 配置 `HTTP_PROXY`/`HTTPS_PROXY` 以通过代理路由流量

这种方法可以处理任何基于 HTTP 的服务，无需编写自定义工具，但会增加证书管理方面的复杂性。

请注意，并非所有程序都遵循 `HTTP_PROXY`/`HTTPS_PROXY`。大多数工具（curl、pip、npm、git）会遵循，但有些可能会绕过这些变量并直接连接。例如，Node.js 的 `fetch()` 默认忽略这些变量；在 Node 24+ 中，你可以设置 `NODE_USE_ENV_PROXY=1` 来启用支持。为了全面覆盖，你可以使用 [proxychains](https://github.com/haad/proxychains) 来拦截网络调用，或配置 iptables 将出站流量重定向到透明代理。

  **透明代理**在网络层面拦截流量，因此客户端无需进行配置即可使用。常规代理要求客户端显式连接并使用 HTTP CONNECT 或 SOCKS 协议。透明代理（如 Squid 或 mitmproxy 的透明模式）可以处理重定向的原始 TCP 连接。

两种方案都仍需 TLS 终止代理和受信任的 CA 证书。它们只是确保流量确实能到达代理。

## 文件系统配置

文件系统控制决定了代理可以读取和写入哪些文件。

### 只读代码挂载

当代理需要分析代码但不进行修改时，应以只读方式挂载目录：
```bash
docker run -v /path/to/code:/workspace:ro agent-image
```


  即便是对代码目录的只读访问也可能泄露凭证。在挂载前，建议排除或清理以下常见文件：

  | 文件                                                    | 风险                                  |
  | ------------------------------------------------------- | ------------------------------------- |
  | `.env`, `.env.local`                                    | API 密钥、数据库密码、密钥            |
  | `~/.git-credentials`                                    | 以明文形式存储的 Git 密码/token        |
  | `~/.aws/credentials`                                    | AWS 访问密钥                          |
  | `~/.config/gcloud/application_default_credentials.json` | Google Cloud ADC token                |
  | `~/.azure/`                                             | Azure CLI 凭证                        |
  | `~/.docker/config.json`                                 | Docker 注册表认证 token               |
  | `~/.kube/config`                                        | Kubernetes 集群凭证                   |
  | `.npmrc`, `.pypirc`                                     | 包注册表 token                        |
  | `*-service-account.json`                                | GCP 服务账户密钥                      |
  | `*.pem`, `*.key`                                        | 私钥                                  |

  建议考虑只复制所需的源文件，或使用类似 `.dockerignore` 的过滤方式。

### 可写位置

如果代理需要写入文件，根据是否希望更改持久化，您有几个选项：

对于容器中的临时工作空间，可使用仅存在于内存中且在容器停止时即被清除的 `tmpfs` 挂载：
```bash
docker run \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=100m \
  --tmpfs /workspace:rw,noexec,size=500m \
  agent-image
```
如果您希望在应用更改前进行审查，覆盖文件系统允许代理写入而不修改底层文件。更改存储在单独的层中，您可以查看、应用或丢弃该层。如需完全持久化输出，请挂载专用卷，但需将其与敏感目录分开。
