# 倡导者工具包

> 一份为内部工程师倡导 Claude Code 所设计的指南：分享内容、解答疑问以及推动团队采用的方法。

本页适用于已经使用 Claude Code 并希望帮助团队采用它的工程师个体。内容涵盖分享内容、解答常见问题、三十天行动计划以及应对常见疑虑的回复。

开发者工具的采用很少源于一次发布通知。它源于团队中某人开始熟练使用该工具、公开讨论它，并使他人易于跟随。作为倡导者所做的工作具有不成比例的影响力：你分享的每个示例都为后来者缩短了学习曲线，你公开回答的每个问题都将个人经验转化为整个团队可以借鉴的积累。你正在成为团队的效能倍增器，而非技术支持中心，本指南正是围绕这一可持续角色定位来构建的。

## 倡导者角色

该角色由三种相互强化的行为构成。

| 行为                       | 实践中的表现                                                                                                                                                     | 重要性                                                                                                                                                                                  |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **分享你的发现**           | 在团队已有的信息渠道（如工程频道、站会讨论串或拉取请求描述）中发布你自己工作中的提示词、截图和小成就。                                                               | 来自你自身代码库的示例比任何外部文档都更具说服力，因为同事可以确切看到该工具如何应用于他们与你共享的问题。                                                                                  |
| **成为被咨询的人**         | 当同事询问你是如何完成某事时，提供你实际使用的提示词，以便他们能直接应用到自己的任务中。                                                                           | 一个具体、可运行的示例消除了从好奇到首次成功使用之间的鸿沟，而多数采用尝试都停滞于此。                                                                                                  |
| **扩大圈子**               | 建立少量轻量级、周期性的习惯，如设立专用频道或每周讨论串，这样即使你的注意力转移，势头也能得以保持。                                                               | 依赖单一人的采用是脆弱的。由共享习惯承载的采用则能持续自我累积。                                                                                                                          |

这些活动大多自然融入你现有的工作。区别仅在于，你需要对你的发现在何处发布、你的回答如何传播，抱有少许额外的意图。

### 预期投入

对自己和你的主管设定期望。以下活动旨在融入正常工作周内，该角色应保持为你现有工作的效能倍增器，而非额外的支持职责。

| 活动                                | 每周时间 | 指导建议                                                                                                                         |
| ----------------------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 发布成就和提示词                    | 约 15 分钟 | 随时用截图和一两句话记录；避免将其转化为正式报告。                                                                                 |
| 在共享频道解答问题                  | 约 20 分钟 | 公开回答一次，之后当问题再次出现时链接回该回答。                                                                                     |
| 主持每周“展示与讲述”讨论串          | 约 5 分钟  | 你发布开场提示词；团队提供内容。                                                                                                   |
| 可选的配对编程或演示                | 0 至 30 分钟 | 保留给真正受阻的同事，在安排时间前提供[快速入门](/en/quickstart)链接。                                                             |

## 分享你的发现

你自身的经历是同事将遇到的最具说服力的材料，因为它针对的是你们共同的代码库、工作流和问题。文档告诉人们什么是可能的；你的帖子则向他们展示在你的环境中什么是真正有效的。

### 什么值得分享

最有用的帖子描述的是同事明天就能复用的技术，而非一个已经完成的结果。技术随着在团队中传播而累积；状态更新则不然。

可复用技术示例：

*   “我发现 @-mention 一个目录是可行的。将它指向 `@src/components/` 并询问哪些缺少测试，就暴露了我遗漏的两个。”
*   “计划模式 (`Shift+Tab`) 会在任何编辑前精确显示哪些文件将被修改，这就是为什么我敢于在共享代码上使用它。”
*   “我配置了一个停止钩子，这样当长时间任务完成时，我会收到桌面通知。配置方法在讨论串中。”
*   “运行 `/init` 会根据仓库生成一个 `CLAUDE.md`，这样助手就不会反复询问我们的惯例了。”

### 在哪里分享

发布到你的团队已经阅读的地方。目标是将示例置于正常工作的路径中，而非创建一个独立的目的地。

| 位置                                            | 最适用于                                                               | 推荐格式                                                                                     |
| ----------------------------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `#claude-code` 或通用工程频道                   | 发现、提示词和“今日所学”时刻                                             | 截图配上一两句背景说明                                                                         |
| 拉取请求描述                                    | 在评审者已阅读的真实代码上展示方法                                       | 一句话，如“Claude 和我完成了这次重构；乐意介绍方法。”                                           |
| 站会或每周书面更新                              | 与主管及上层经理规范使用习惯                                             | 一句话描述一个具体成果                                                                         |
| 团队维基或内部文档                              | 持久化的模式、自定义技能和 `CLAUDE.md` 示例                               | 一个简短页面，从频道主题链接以便可发现                                                         |

### 有效的格式

截图配上一行上下文说明，或简短的前后对比描述，通常是合适的详细程度。保持每篇帖子足够简短，让快速浏览的人也能抓住要点。长篇报告倾向于被“稍后阅读”然后遗忘，而带有截图的短帖则倾向于被复制和尝试。

下面的示例帖子展示了合适的语气和长度；请根据需要调整，而非逐字复制。
```text
Learned today that @-mentioning a directory works. I pointed it at
@src/components/ and asked which components were missing tests, and it
surfaced two I had forgotten about.
```

```text
I configured a Stop hook so I receive a desktop notification when a long
task completes. I started a refactor, stepped away, and was notified when
it finished. Configuration is in the thread.
```

```text
Plan mode is the reason I am comfortable using this on code that matters.
Press Shift+Tab until you see "plan"; it lays out exactly which files it
intends to touch before changing anything.
```
## 成为被提问的对象

一旦你分享了几个示例，问题就会接踵而至。这正是 Champion 角色发挥最大杠杆作用的地方，因为一个好的回答通常能一次性为许多关注同一频道的其他人扫清障碍。

### 用提示词而非解释来回答

当同事问你是如何完成某件事时，最有用的回答是你实际使用的提示词。让他们用这个提示词在自己的问题上运行，比你写任何描述都能学到更多，并且这给了他们一个可以立即采取行动的东西。
```text
Colleague: How did you get it to find that race condition?

Champion: I asked, "The test in @tests/scheduler.test.ts is flaky, figure
out why," and it traced two unjoined promises in the scheduler. Try the
same phrasing on your test.
```
### 直接指向功能而非文档

在当下，像“试试计划模式，按 `Shift+Tab` 切换直到看到它”这样的回复，比一个文档链接更有用。如果对方之后需要更深入的信息，他们自己会找到的；此时他们需要的是能立即帮他们突破障碍的那个具体功能。

### 你可能会听到的问题

| 问题                                             | 建议的回复                                                                                                                                                                                                                   | 后续资源                                                |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| “我应该先用它来做什么？”                         | 建议一个真实但受限的任务，最好是用户因为繁琐（而非困难）一直推迟的缺陷或杂活。                                                                                                                                              | [常见工作流](/en/common-workflows)                      |
| “我怎么能信任它处理我的代码？”                   | 介绍计划模式：按 `Shift+Tab` 循环进入该模式，Claude 会精确提议它打算修改什么，在用户批准之前不会修改任何内容。                                                                                                              | [权限](/en/permissions)                                 |
| “花费精力去设置值得吗？”                         | 安装大约需要两分钟，在终端中运行，并且不需要 IDE 扩展。只需运行一次 `/init` 即可开始工作。                                                                                                                                  | [快速入门](/en/quickstart)                              |
| “它产生了错误的结果。”                           | 鼓励他们将失败的结果反馈给 Claude。粘贴错误消息或失败的测试用例比重新表述原始请求有效得多。                                                                                                                                 | [常见工作流](/en/common-workflows)                      |
| “它不理解我们代码库的约定。”                     | 建议运行 `/init` 生成 `CLAUDE.md` 文件，然后添加团队的约定、测试命令以及任何应避免的目录。                                                                                                                                 | [记忆](/en/memory)                                      |
| “这不就是自动补全吗？”                           | 进行一次简短的演示，让 Claude 解释一个不熟悉的文件、跨服务追踪一个缺陷，或者起草一个迁移计划。这些任务需要跨仓库推理，而不是仅仅补全一行代码。                                                                             | 两分钟现场演示                                          |
| “安全性和数据处理方面呢？”                       | 将此问题转交给你的管理员。你组织的部署和数据处理策略已经配置好了，倡导者不应即兴回答此问题。                                                                                                                                | [安全](/en/security) · [数据使用](/en/data-usage)       |

## 扩大影响圈

目标不是构建一个程序或主导一次推广。而是建立少量轻量级习惯，以便在您停止积极推动后，动力仍能持续。当频道中的问题开始由你以外的其他人解答时，这个角色便已尽其责。

### 通常行之有效的模式

| 模式                                   | 如何执行                                                                                                                                                                                                                                   | 所需精力                                |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------- |
| 专用频道                               | 创建一个 `#claude-code` 频道（或在现有频道中创建一个定期讨论串），置顶 [快速入门](/en/quickstart) 链接和一个优秀的示例，并公开回答问题，这样每个答案都能惠及所有关注者。                                                                    | 设置大约五分钟，之后只需投入少量精力    |
| 每周展示讨论串                         | 每个星期五发布“这周 Claude 帮你完成了什么？”不需要准备、幻灯片或会议；截图和简短描述就足够了。                                                                                                                                              | 每周约两分钟                            |
| 分享自定义技能                         | 发布你最有用的 `.claude/skills/<name>/SKILL.md` 文件，例如一个在提交前运行测试和代码检查的 `/ship` 技能，附上一行描述。由于技能是纯 Markdown，同事可以立即采用。                                                                             | 每项技能约五分钟                        |
| 根据你的使用情况生成设置指南           | 在你花过真实时间的项目中运行 `/team-onboarding`。Claude 会扫描你最近的会话、命令和 MCP 服务器，然后生成一份指南，新队友可以将其作为第一条消息粘贴以重现你的设置。将其置顶在频道中。                                                         | 约两分钟                                |
| 为第一个任务结对                       | 为任何刚开始使用的人提供一个十五分钟的结对会话。一个在他们自己代码上取得的成功结果比任何演示都更有说服力。                                                                                                                                  | 每人约十五分钟                          |
| 识别下一位倡导者                       | 向你提问最多的同事通常已准备好担任这个角色。将此页面转发给他们，并与你分担频道责任。                                                                                                                                                        | 可忽略                                  |

### 三十日行动手册

如果有一个粗略的计划会有帮助，以下顺序反映了在大多数团队中通常有效的方法。请根据你的具体情况自由调整。


    创建一个频道，置顶[快速入门](/en/quickstart)，并发布两三个您自己的包含提示词的示例。

    **表明它正在运作：** 几位同事做出反应或回复，并且频道中至少有人提出一个问题。



    启动每周演示分享帖子，公开回答所有问题，并分享一个自定义技能或 `CLAUDE.md` 代码片段。

    **表明其有效的标志是：** 除了您之外，其他人也发布了他们自己的示例。



    提供两到三次简短的配对会话，并将最常见的问题和答案整理成一条置顶的常见问题解答消息。

    **成功标志：** 你会看到同事们的重复使用，即相同的同事会持续参与，而非尝试一次后便停止。



    确定第二位支持者，并与你的领导或管理员简要分享有效和无效之处。

    **表明其有效：** 频道中的问题开始由你以外的人回答。


### 当有人想深入探索时

您是温暖的引路人，而非完整的培训计划。当同事从“我该试试这个吗”阶段进入“如何熟练使用它”阶段时，请引导他们查阅[快速入门](/en/quickstart)和[常见工作流程](/en/common-workflows)页面。这些页面包含简短章节，介绍那些确实有用但难以自行发现的功能。

## 回应常见疑虑

保持健康的怀疑态度是正常的；工程师应对涉及代码的工具保持谨慎。最有效的回应往往不是争论普遍情况，而是：承认疑虑，提供简短的新视角，并提议在对方自己的代码上进行一次具体演示。大多数疑虑只需一次成功体验即可消除。

| 疑虑                                         | 建议回应                                                                                                                                                           | 可提供的证据                                           |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| "没有它我更快。"                               | 对于用户经常编写的代码，这可能确实如此。建议在其倾向于避免的工作上尝试：遗留文件、不熟悉的服务或测试脚手架，这些场景杠杆率最高。                                         | 分别用两种方式计时完成一项繁琐任务并比较结果。           |
| "我不信任AI接触生产代码。"                       | 同意任何更改都不应未经查阅就上线。计划模式配合常规差异审查意味着工程师审查过的更改才会被应用，这与任何拉取请求的标准相同。                                             | 在真实文件上演示计划模式。                               |
| "这会让初级工程师变得更弱。"                      | 如果用得好，它是一个有效的解释工具。鼓励初级工程师在要求修改任何内容之前，先让Claude解释文件及其调用点。                                                               | 一起运行"解释@file及其调用位置"。                       |
| "我试过一次，它产生了幻觉。"                      | 这通常是上下文问题，而非模型问题。使用@提及相关文件、运行`/init`、并提供实际的错误输出通常能解决。                                                                   | 使用正确的`@`上下文重新运行他们的原始提示词。            |
| "我们没时间学习另一个工具。"                      | Claude Code是一个终端命令，而非平台。如果第一次会话未能产生价值，将其搁置是合理的。                                                                                 | 两分钟安装后解决一个真实bug。                            |

## 快速参考表

以下技术最能可靠地帮助用户从初次试用转向日常使用。可将此表格固定在某个频道或单独分享。

| 技术                        | 如何应用                                                                                                                                                         |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 提供正确的上下文             | 使用`@file`或`@directory/`引用，或直接粘贴错误或日志输出。提供相关上下文比精心设计的提示词更有效。                                                                    |
| 编辑前审查计划               | 按`Shift+Tab`进入计划模式。Claude将在执行更改前描述拟议的更改供您批准。                                                                                              |
| 让它学习您的仓库             | 运行`/init`生成`CLAUDE.md`文件，然后添加您的规范、测试命令以及任何不应修改的目录。参见[记忆](/en/memory)。                                                            |
| 复用工作流程                 | 在`.claude/skills/<name>/`中保存一个`SKILL.md`文件，以创建整个团队都可使用的`/name`技能。参见[技能](/en/skills)。                                                         |
| 在长任务中保持信息同步         | 配置一个停止钩子，以便在长时间运行的任务完成时收到桌面通知。参见[钩子指南](/en/hooks-guide)。                                                                         |
| 从错误结果中恢复             | 与其重新表述请求，不如将失败的测试或堆栈跟踪粘贴回Claude，并要求它处理该特定失败。                                                                                   |
| 保持编辑精准                 | 请求一个差异，或明确说明"只修改X"。当范围明确时，Claude会严格遵守。                                                                                                  |

  Claude Code 会频繁更新。在内部分发此材料之前，请先根据[文档首页](/en/overview)核对版本特定细节。
